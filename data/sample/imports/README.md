# Sample files for "Import data" (synthetic)

Four small files to try `POST /api/v1/imports` and the web app's **Import data** dialog.

> **Everything here is synthetic.** The files are generated by
> [`scripts/make_sample_imports.py`](../../../scripts/make_sample_imports.py) from fixed random
> seeds around the synthetic demo plot `PLT-DEMOIN`
> ([`data/sample/plots/india-mango-farm.json`](../plots/india-mango-farm.json)). They are not a
> real farm, not real trees and not a survey, and they hold no personal data. Released under
> [CC0 1.0](https://creativecommons.org/publicdomain/zero/1.0/): copy and reuse them freely.

| File | What it is | What the API makes of it (linked to `PLT-DEMOIN`) |
| --- | --- | --- |
| `demo-boundary.kml` | One polygon of 7 vertices: the demo plot's boundary, named "Demo mango orchard (synthetic)". | `kind: "boundary"`, area about 2.13 ha. |
| `demo-corners.csv` | The same 7 corners as a list (`name,lat,lon`). | `kind: "boundary"` (corners read in file order, ring closed automatically), same area, with a warning saying so. With `purpose=trees` the 7 points are counted as 7 trees instead. |
| `demo-crowns.geojson` | 220 small crown polygons, each with a numeric `score` (22 of them below 0.5), all inside the plot. Shaped like the output of a tree-crown segmentation tool (a polygon layer with a score column). | `kind: "tree-crowns"`, `trees.count` 198 at the default `min_confidence` 0.5 (all 220 at `min_confidence=0`), all 198 inside the plot, `canopy_cover_fraction` about 0.15. |
| `demo-orchard.laz` | A classified point cloud (LAZ, EPSG:32643 = WGS 84 / UTM zone 43N), 183 757 points, about 4.5 points per m², 200 m x 204 m: the plot plus a 12 m margin of neighbouring trees. 472 cone-shaped trees (3-7 m) stand on a 9 m grid with jitter and 8 % gaps; ground is class 2, crowns class 5. | `kind: "point-cloud"`, about 472 tree tops (472 matched to the planted trees within 1 m, none missed, none extra), 243 inside the plot (242 planted inside), mean height about 5.0 m. |

The file sizes are small (the LAZ is under 1 MB) so they are safe to keep in the repository.

## Try them

With the API running in demo mode (`ATLAS_MODE=demo`), from the repository root:

```bash
# a boundary: read it, then POST /plots with source "import" to use it as the plot
curl -s -F file=@data/sample/imports/demo-boundary.kml http://localhost:8000/api/v1/imports

# crowns counted inside the demo plot, keeping only scores of 0.7 or more
curl -s -F file=@data/sample/imports/demo-crowns.geojson \
        -F plot_id=PLT-DEMOIN -F min_confidence=0.7 http://localhost:8000/api/v1/imports

# a point cloud: tree tops, heights and the count inside the plot
curl -s -F file=@data/sample/imports/demo-orchard.laz \
        -F plot_id=PLT-DEMOIN http://localhost:8000/api/v1/imports
```

Add `-H "X-API-Key: ..."` when `ATLAS_API_KEYS` is set. The response is an `ImportRecord`
(see [`docs/architecture/api-contract.md`](../../../docs/architecture/api-contract.md), section
"Imports"); how the numbers are obtained is explained in
[`docs/architecture/imports-and-detection.md`](../../../docs/architecture/imports-and-detection.md).
The uploaded file itself is never stored: only the derived record is kept.

The same files open in QGIS (KML, CSV, GeoJSON) and in CloudCompare (LAZ); recent QGIS
versions open the LAZ too.

## Regenerate or verify

```bash
python3 scripts/make_sample_imports.py            # rewrite the four files
python3 scripts/make_sample_imports.py --check    # exit 1 when a file is out of date
```

The generator uses fixed seeds and a fixed LAS creation date, so the same code and library
versions give the same bytes. The LAZ bytes also depend on the `laspy`/`lazrs` version, so
`--check` can report the LAZ as stale after those packages are upgraded: regenerate it, and
check that the numbers in the table above still hold.

## What these files are not

The crowns are drawn from a simple model (a circle of radius 1 m + 0.25 x height, with a little
random wobble), and the point cloud is made of cones standing apart on flat ground. Real crowns
touch and overlap, real clouds have noise and gaps, and a real segmentation tool will not give
the same polygons. Use these files to learn the workflow and to test the software, not to judge
how accurate the detection is on real land; compare any real result with a field count.
