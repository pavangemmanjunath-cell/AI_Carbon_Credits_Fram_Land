# Sample data (synthetic)

Everything in this folder is **synthetic** and safe to publish. None of it is a real farm, tree or survey, and none of it
holds personal data. Never add a real farm boundary here: see the
[privacy design](../../docs/privacy/privacy-design.md). All exchange formats are JSON (GeoJSON for geometry), apart
from the import samples, which are the file formats the Import dialog accepts.

| Folder | What it holds | Made by |
| --- | --- | --- |
| [`plots/`](#plots) | Three demo plots with an inventory | By hand, from generated polygons |
| [`responses/`](#responses) | What the API returns for the demo plots, tree age and imagery | `scripts/make_sample_responses.py`, `scripts/make_sample_tree_age.py` |
| [`imports/`](imports/README.md) | Four files to try "Import data": KML, CSV, GeoJSON crowns and a LAZ point cloud | `scripts/make_sample_imports.py` |

## plots

`plots/*.json` are three demo plots: an India mango orchard, a US pecan agroforestry plot and an EU olive grove. Each has
an irregular polygon generated around a rural point, a tree inventory and a note. In demo mode (`ATLAS_MODE=demo`,
`ATLAS_SEED_DEMO=true`, which is the default) the API seeds them on startup with stable ids: `PLT-DEMOIN`, `PLT-DEMOUS`
and `PLT-DEMOEU`. They are the same farms as the ones in [`examples/`](../../examples/README.md).

## responses

`responses/*.json` are the JSON that the API returns in demo mode, saved as files. They serve four purposes: offline data
for the web app, fixtures for the QGIS plugin's tests, the contract test, and examples for the documentation.

| Files | Request they record | Generated by |
| --- | --- | --- |
| `health`, `regions`, `species` (for `IN`), `methodologies`, `attribution`, `geocode` | The configuration and place-search endpoints | `make_sample_responses.py` |
| `plots`, `plot`, `plot-public` | The demo plot `PLT-DEMOIN`, as the owner sees it and as the public view | `make_sample_responses.py` |
| `analysis`, `vegetation`, `cube` (NDVI, 36 months), `trees`, `carbon-estimate`, `policy-eligibility`, `market-scenario` | The plot's assessment chain | `make_sample_responses.py` |
| `simulate-IN`, `simulate-US`, `simulate-EU` | `POST /simulate` for mango, pecan and olive | `make_sample_responses.py` |
| `explain`, `report-meta`, `report.json`, `report.html` | The explanation of a set of indicators and a generated report | `make_sample_responses.py` |
| `tree-age-IN`, `tree-age-US`, `tree-age-EU` | `POST /tree-age/assess`, described below | `make_sample_tree_age.py` |
| `imagery-providers-IN`, `imagery-providers-US` | `GET /imagery/providers?country=IN` and `?country=US` | `make_sample_tree_age.py` |

The three tree-age samples describe synthetic trees only (no coordinates and no plot are involved):

| Sample | Trees | What it shows |
| --- | --- | --- |
| `tree-age-IN.json` | 25 mango trees, 60 years old, on a farm in Haryana (`IN-HR`), no measurements | A Tier 1 estimate by age, with the Indian rules that apply |
| `tree-age-US.json` | 3 black walnut trees, 45 years old, in an urban setting in Oregon (`US-OR`), no measurements | The same assessment for a yard tree |
| `tree-age-EU.json` | 4 oaks, 80 years old, in Berlin (`DE-BE`), girth 190 cm, height 22 m | A Tier 2 estimate from the measurements, with the age as context |

The samples are made in development mode, so rules that still await confirmation from a primary source appear with
`verification_status: pending` (two in the India sample, one in the EU sample). A production deployment withholds them and
lists their ids in `withheld_rule_ids`.

In the imagery samples, the Esri key is forced empty, so `esri-world-imagery` is listed as unavailable and no key can
reach a committed file.

### Where the responses are used

- `tests/integration/test_contract_fixtures.py` compares the field names of six of them (`plot`, `analysis`,
  `carbon-estimate`, `policy-eligibility`, `market-scenario`, `regions`) with what the demo API returns now, so an
  accidental change of the contract fails the test.
- `integrations/qgis-plugin/tests/test_qgis_formatting.py` formats them the way the plugin does.
- `npm run fixtures:demo` (in `apps/web`) copies 20 of them, and the report handle, into `apps/web/public/demo/`, which
  is the web app's data when the API is offline. The tree-age and imagery samples, `plot-public` and `report-meta` are
  not copied: those pages have no offline fallback.
- They are also examples of the response shapes described in the
  [API contract](../../docs/architecture/api-contract.md).

## Regenerating

```bash
make samples     # all of the following, then the web demo fixtures
python3 scripts/make_sample_responses.py        # the v0.1 responses (health, plot, analysis, estimate, report, ...)
python3 scripts/make_sample_tree_age.py         # tree-age-*.json and imagery-providers-*.json
python3 scripts/make_sample_imports.py          # the four files in imports/
cd apps/web && npm run fixtures:demo            # copy the responses into apps/web/public/demo/
```

The scripts call the API in-process (FastAPI's `TestClient`): nothing listens on a port and nothing leaves the machine.

| Script | Deterministic | `--check` |
| --- | --- | --- |
| `make_sample_responses.py` | No: the files carry the time they were generated, so a re-run changes them | No |
| `make_sample_tree_age.py` | Yes: the clock is pinned (`2026-10-05T00:00:00Z`, `as_of_year` 2026) and the Esri key is blank | Yes: exits with 1 when a file is out of date |
| `make_sample_imports.py` | Yes: fixed seeds and a fixed creation date (the LAZ bytes also depend on the `laspy` and `lazrs` versions) | Yes |

Regenerate after an intentional change of the contract, the parameters or the rules, review the diff, and commit the
files together with the change that caused it. The version number appears in some responses, so
[the release process](../../docs/developer-guide/release-process.md) regenerates them for a release.

In demo mode every provenance block is labelled `synthetic-demo`. Every carbon figure in these files is a scenario
estimate with `certified: false`, not a carbon credit.
